Why Data Wrangling?

Analysts spend 50–80% of their time preparing data, not modeling it.

  • Raw public health data is messy: inconsistent units, irrelevant columns, impossible values, mixed granularities.
  • dplyr gives you a small vocabulary of verbs, each doing one thing well:
Verb Question it answers
filter() Which rows do I keep?
arrange() In what order should rows appear?
select() Which columns do I keep?
rename() What should columns be called?
mutate() What new columns do I need?

Today’s Dataset: Global Health (gm)

The gm dataset from the r02pro package tracks health indicators for world countries over time.

library(r02pro)
library(dplyr)

gm   # 65,531 rows x 33 columns
  • country, continent, year, population
  • life_expectancy, child_mortality, sugar, food_supply
  • smoking_male, smoking_female, GDP_per_capita, HDI

One row = one country in one year.

The Native Pipe |>

The pipe takes the object on its left and passes it as the first argument to the function on its right.

Nested (hard to read)

head(filter(gm, year == 2008), 3)

Read from the inside out. 😵

Piped (reads like a recipe)

gm |>
  filter(year == 2008) |>
  head(3)

Read top to bottom: take gm, then filter, then show 3 rows.

Tip

Type |> quickly with Cmd/Ctrl + Shift + M (after enabling the native pipe in RStudio: Tools → Global Options → Code → “Use native pipe operator”).

filter(): Keeping Rows That Match

filter() keeps rows where a logical condition is TRUE (the same logicals you built in Week 2!).

# Countries observed in 2008 with life expectancy over 80
gm |>
  filter(year == 2008, life_expectancy > 80)
  • Multiple conditions separated by commas are combined with AND (&).
  • Use | explicitly for OR:
# Rows from Africa OR Europe
gm |> filter(continent == "Africa" | continent == "Europe")

# Equivalent shortcut with %in%
gm |> filter(continent %in% c("Africa", "Europe"))

filter() and Missing Values

filter() silently drops rows where the condition evaluates to NA!

# Rows where sugar consumption exceeds 40 g/day
gm |> filter(sugar > 40)          # NA rows are gone, no warning

# Keep only rows where sugar was actually measured
gm |> filter(!is.na(sugar))

# Explicitly inspect the missing rows
gm |> filter(is.na(sugar))

Warning

Always ask: “How many rows did I lose, and why?” Check with nrow() before and after filtering.

arrange(): Ordering Rows

# Lowest child mortality first
gm |>
  filter(year == 2008) |>
  arrange(child_mortality)

# Highest first: wrap in desc()
gm |>
  filter(year == 2008) |>
  arrange(desc(life_expectancy))

# Tie-breakers: sort by continent, then by population within continent
gm |> arrange(continent, desc(population))
  • NA values are always placed last, regardless of direction.

Cycle 2: Selecting & Renaming Columns

select(): Keeping Columns

With 33 columns, most analyses need only a handful:

# Keep identification + outcome columns
gm |> select(country, year, life_expectancy)

# Keep a consecutive range of columns
gm |> select(country:year)

# Drop columns with a minus sign
gm |> select(-population, -HDI)

select() Helper Functions

Match columns by name pattern instead of typing them all:

# All smoking-related columns
gm |> select(country, year, starts_with("smoking"))

# All columns measured separately for each sex
gm |> select(country, year, ends_with("_male"), ends_with("_female"))

# Any column mentioning cancer
gm |> select(country, year, contains("cancer"))
  • starts_with(), ends_with(), contains() are your workhorses.
  • where(is.numeric) selects by column type.

rename(): Clear Column Names

rename(new_name = old_name), and the rest of the data stays untouched:

gm |>
  select(country, year, life_expectancy, GDP_per_capita) |>
  rename(life_exp = life_expectancy,
         gdp = GDP_per_capita)

Tip

select() can rename while selecting: select(life_exp = life_expectancy). Use rename() when you want to keep all other columns.

Cycle 3: Creating New Variables with mutate()

mutate(): New Columns from Old

mutate() adds columns to the end of the data frame; existing columns are preserved.

# Units (see ?gm): GDP_per_capita is in $1,000, population is in 1,000 people,
# so their product is in millions of dollars.
gm |>
  filter(year == 2008) |>
  select(country, population, GDP_per_capita) |>
  mutate(gdp_millions = GDP_per_capita * population)
  • Right side is any vectorized expression (Week 2 arithmetic!).
  • Check the units before you multiply or divide. ?gm documents them.
  • New columns can be built from columns you just created:
gm |>
  mutate(gdp_millions = GDP_per_capita * population,
         gdp_billions = gdp_millions / 1e3)

mutate() with Logical Columns

A comparison creates a TRUE/FALSE column, ready for later filtering:

gm |>
  filter(year == 2008) |>
  select(country, life_expectancy) |>
  mutate(above_80 = life_expectancy > 80)
# Unit conversions are classic mutate() one-liners
# population is recorded in thousands of people (?gm)
gm |>
  mutate(pop_millions = population / 1e3)

Warning

mutate() never changes the original gm object. To keep your work, assign the result: gm2008_clean <- gm |> ...

Putting It All Together

A complete wrangling pipeline, start to finish:

smoking_2004 <- gm |>
  filter(year == 2004, !is.na(smoking_male), !is.na(smoking_female)) |>
  select(country, continent, population,
         starts_with("smoking")) |>
  rename(male = smoking_male, female = smoking_female) |>
  mutate(gap = male - female,
         pop_millions = population / 1e3) |>   # population is in thousands
  arrange(desc(gap))

head(smoking_2004)

Every verb answers one question. The pipeline tells the whole story.

Cycle 4: Pipelines in Practice + Quiz

Debugging Pipelines: Read Them Like Steps

Run a pipeline one verb at a time to find where things go wrong:

gm |>
  filter(year == 2008)            # Step 1: run up to here. Rows look right?

gm |>
  filter(year == 2008) |>
  select(country, sugar)          # Step 2: expected columns present?
  • Highlight everything up to (but not including) a pipe and press Cmd/Ctrl + Enter.
  • nrow(), names(), and head() are your cheap diagnostic probes.

Common dplyr Pitfalls

1. = vs == inside filter()

gm |> filter(year = 2008)   # ERROR
gm |> filter(year == 2008)  # correct

2. Forgetting to assign

gm |> mutate(x = sugar * 7)
# printed... and discarded!

3. Quoting column names

gm |> select("country")  # works, but
gm |> select(country)    # idiomatic

4. Overwriting your raw data

gm <- gm |> filter(year == 2008)
# original gm is gone for this session!
# Use a new name: gm_2008

AI Corner: Auditing an AI-Written Pipeline

An AI assistant produced this code for “average sugar consumption in Asia in 2008”:

gm %>%
  group_by(continent) %>%
  summarize(mean_sugar = mean(sugar))

Three audit findings:

  1. It used verbs (group_by, summarize) we can’t verify yet, when a simple filter() + mean() answers the question.
  2. It never filtered year == 2008, so it silently averages all years.
  3. mean(sugar) returns NA because missing values were never handled.
# A verifiable Week-5 answer:
asia_sugar <- gm |> filter(year == 2008, continent == "Asia", !is.na(sugar))
mean(asia_sugar$sugar)
